# Golden transcripts: notes

Guide 7.2 (the 20 scripts) and 7.4 (the five behaviors outside the contract surfaces). This file lists the decisions, the port bugs that the scripts found, and what is not done.

## Port bugs and gaps that the scripts found

1. **`pre_tool_call` did not fail closed** (`packages/plugin-host/src/hooks.ts`). Upstream treats `pre_tool_call` as a policy hook. A callback that throws gives a block with the text `pre_tool_call plugin callback <name> raised <ErrorName>: <message, 200 characters>`. A callback that runs past the time budget gives a block with the text `pre_tool_call plugin callback timed out or is still running`. The port logged the failure and went on, so a crashing guard let the tool run. Read from `hermes_cli/plugins_dispatch.py` (`_run_hook_callbacks`, `_policy_error_block_directive`). Fixed. Found by `hook-crashes` and `hook-time-budget`. The old test "crashes do not block" was wrong and is replaced.
2. **A block with no message blocked** (same file). Upstream ignores a `block` directive with no message or an empty one, because the message is the tool result (`_get_pre_tool_call_directive_details`). The port blocked with "blocked by plugin". Fixed.
3. **No hook in the loop** (`packages/session-actor/src/loop.ts`). The plugin host had a `HookDispatcher`, but nothing in the loop called it. Added the seam `LoopHooks` (a structural type, so session-actor does not depend on plugin-host). The loop calls `preToolCall` once for each tool call before the tool runs. On a block the tool does not run, and the result is `{"error": "<message>"}`, written as Python's `json.dumps(..., ensure_ascii=False)` writes it (a space after the colon). If the dispatcher itself throws, the call goes on (upstream `_pre_tool_block`). The keyword arguments are those of upstream: `tool_name`, `args`, `task_id`, `session_id`, `tool_call_id`, `turn_id`, `api_request_id`, `middleware_trace`, `conversation_id`. Found by the hook scripts.
4. **Tool results were not in call order** (`loop.ts`, `#plan`). When one answer had a terminal call first and then calls that the loop answers without the executor (an unknown tool, bad arguments, `todo_list`), the inline results were written first. The rows and the next request had `call_2, call_3, call_1`. Upstream appends the results in the order of the calls. Fixed: once an operation is planned, the first call that would be answered inline waits for the next pass, after the operation results are written. Consequence: `[terminal, todo, terminal]` now runs the first terminal call alone, then the todo call, then the last terminal call. Upstream also runs a batch in sequence when it has a tool that is not parallel-safe. One edge: a terminal call that comes after an operation and is blocked by a hook has run its hook once when the loop stops at it, and runs it again in the next pass. Found by `tool-error-text`.
5. **No provider fallback in the loop** (the providers NOTES list it under "Not done"). Added the seam `LoopFallback` (`{client, model}`) next to the model client. On a 429 or 402 from the primary (the "eager fallback" of upstream, `packages/providers/src/retry.ts`), the loop builds the request again for the fallback client from the stored messages, writes it into `pending_call.request` with `data.target = "fallback"` in one commit, and sends it. Later calls of the same turn build for the fallback too. The next turn starts on the primary again. Not done: the other fallback triggers of `decide()` (repeated timeouts and overloads), the primary cooldown, and the summary call of a compaction (it keeps the wait-and-resend path). Found by `provider-fallback-429`.

All fixes have a test: `hooks.test.ts` in plugin-host, `seam.test.ts` and the scripts in this package.

## Decisions

- **One record format.** The record is `hermesd-golden/1` of `packages/session-actor/src/model/recorder.ts`, unchanged. The upstream side writes the same format (`scripted-server/assemble.mjs`).
- **The runner uses the real parts.** The loop runs through `createLoopWorld` of `packages/faults` (both Node modes), the provider clients and scripted models of `packages/providers`, and the executor model. Hook plugins are written as JS files into a temporary folder and loaded by the real `PluginHost` (`manifest`, `register(ctx)`, `provides_hooks` check, directory-order dispatch). Plugins are loaded in script order, not folder order, so `three-plugins-hook-order` tests the dispatch sort and not the load order.
- **Both modes must agree.** `runScript` plays a script on `node/durable-objects` and `node/rivet` and throws if the records differ.
- **Deterministic by construction.** The platform clock is virtual. Tool call ids come from the script or from the scripted model (`call_<step>_<n>`). The Codex `prompt_cache_key` is a hash in `packages/providers` and is the same in each run. The record has no timestamps, row ids, message uids or call ids. A test greps the committed files for ISO timestamps and UUIDs.
- **Waiting.** The runner sends an input and waits for the reply. When the world is quiet and an obligation is open (a 429, a dropped stream), it moves the virtual clock. When no obligation is open (a hook waiting for its real timer), it sleeps 10 ms. The hook time-budget script uses 200 ms of real time.
- **Commands.** A tool call carries a plain shell string (`echo hello`). The script's `commands` map gives the simulated result. Upstream runs the real command. So both sides see the same tool-call arguments.
- **Request path and host.** The port requests use `http://127.0.0.1:8089/v1/...`, the address that the scripted server has by default, because some provider quirks depend on the URL. Nothing connects to it in the port run.
- **Dates.** The comparator treats any `YYYY-MM-DD` in a string as equal, because the compaction summary prompt has the date of the day (the port uses the virtual clock, upstream the real date).
- **What the scripts ignore for upstream today.** `@system` and `@tools`. The loop runs with a short test system prompt and three tools (`terminal`, `todo_list`, `clarify`). Upstream sends its full prompt and its own tool list. The prompt builder (`packages/prompt`) and the tool registry are not in the loop yet. When they are, remove these two entries from the `ignore` lists. `compare --strict` shows the differences now. The Codex script also ignores `prompt_cache_key`, which is likely to depend on the session id (not checked).
- **Key order.** Request bodies are compared as parsed JSON (providers NOTES, "Wire key order"). Array order counts.
- **Skipped, not passed.** A script with no upstream transcript is a skipped test with the reason. It is never a pass.

## What is not done

- **No upstream transcript exists.** Upstream was only read, never run. `UPSTREAM.md` is written from static reading, and nobody has followed it. The first person to do it should expect to fix some config keys and flags. The Bedrock endpoint override and the context-length key are the two that could not be found. The shape of `payload_json` in upstream's `session_admissions` is a guess (`assemble.mjs` takes the first of `input`, `text`, `message`).
- **The five behaviors of guide 7.4.** Four have a script here: dropped stream, cancellation during a tool, hook ordering, and tool error text. Cancellation is covered at one point of the turn in the golden set (during a tool) and at one more (during the model call, `interrupt-mid-call`); the other points are in `packages/faults/src/loop/cancel.test.ts`. The tool error text covers three failures, not the twelve of the guide: the twelve error texts of the providers are in `packages/providers/src/errors.test.ts`. Provider authentication and key rotation have no script, because a scripted model cannot show them in a request body; they are in `packages/providers/src/router.test.ts`.
- **The approval gate of `pre_tool_call`.** Upstream sends `{action: "approve"}` to a human approval gate and blocks if it is not approved. `modify` rewrites the arguments. The seam treats both as "go on". The plugin-host NOTES list this.
- **The hook runs in the planning step.** A crash before the commit replays the step and runs the hook again. A hook should not count on one call.
- **Terminal output shape.** The port writes the terminal result as compact JSON (`{"output":...}`). Python writes `{"output": ..., "exit_code": 0, "error": null}` with spaces. The first recording will show it. The fix is in `packages/session-actor/src/tools/terminal.ts` (write the Python form), not in the comparator.
- **Streaming scripts.** Only `dropped-stream-mid-token` streams. The streamed forms of the other modes are in `packages/faults/src/loop/providers.test.ts`. The scripted server does not serve Bedrock streaming (binary event stream).
- **`session_admissions` upstream.** `hermes chat -q` may not write that table. See `UPSTREAM.md`.

## Worktrees

`bun install` gives each workspace package its own `node_modules`, with links to the workspace folders it declares (`packages/<package>/node_modules/@hermesd/*`, relative links). A package can import only what its `package.json` lists. Run `bun install` in a new git worktree before `bun run check`, so its links point at the worktree's own packages and not the main checkout's.
